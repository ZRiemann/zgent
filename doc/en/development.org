* Development guide

[[file:readme.org][Documentation]] | [[file:../zh-CN/development.org][中文版]]

** Collaboration

The user leads the core code framework, key logic, design decisions, and
idea validation. Keeping the complete framework understandable to the user
is a project goal, not merely a review step after agent implementation.

Agents normally complete auxiliary code, documentation, build integration,
and focused checks around the user's existing code and stated direction.
Explain the intended change before editing code. When a task affects the
core framework or a key design, describe its basis and impact and follow
the user's explicit direction rather than independently expanding the design.
An explicitly delegated task should proceed within its authorized scope;
the supporting role does not require confirmation for every routine step.

Prefer small, understandable changes. Do not grow abstractions or copy
zeta_agent subsystems solely to achieve apparent completeness. Its designs
are reference material until the user chooses an applicable direction.

** ZetaX ownership and reuse

zgent follows all ZetaX conventions and constraints:

- =zeta_forge= owns shared build tooling, third-party dependency management,
  and installed dependency configuration. Check Forge before adding dependencies;
  do not introduce an application-local Conan graph or vendor third-party source.
- =zpp= owns reusable C++ infrastructure and wrappers, including logging,
  configuration, and lifecycle helpers. Check its existing capabilities before
  implementing a duplicate; reusable additions belong at that boundary.
- =zsa= owns deployment, operations, host configuration, secrets provisioning,
  and shared automation. Keep those responsibilities outside this application.
- =zgent= owns its application framework, behavior, development configuration,
  documentation, and thin project-specific build integration.

Explain proposed cross-repository placement before crossing the authorized
scope. Preserve unrelated changes, staged scope, runtime configuration, and
explicit proxy settings. Do not modify third-party or generated files without
an explicit request.

** Runtime ownership

=z::app::server= retains its =z::server= base and owns both runtime members.
Its NNG owner uses the installed zpp wrapper. The small local =hpx_runtime=
encapsulates callback-based HPX initialization/finalization because zpp's
existing server/main adapters do not provide a composable runtime owner.
This application-specific choice does not add a new zpp public interface.

=configure()= validates settings without starting a runtime. Blocking =run()=
starts NNG, enters HPX, runs the business loop and both cleanup hooks inside
HPX, then releases NNG after HPX returns. A server/runtime owner is noncopyable,
nonmovable, and supports one run attempt; it is not a restartable or concurrent
host interface. The first business/cleanup error is preserved.

Application business concurrency belongs to HPX. Do not create application OS
threads, private executors, or blocking business loops. NNG callbacks may
validate/copy/decode and hand work to HPX; they must not execute business logic.
When communication clients are added, stop their producers in =stop()= and
drain/cancel callbacks and tasks in =wait_stop()= before finalization. Neither
hook currently owns clients. See [[file:../../BUILD.org][BUILD.org]] for exact configuration and
signal behavior. Vault/key loading is outside the implemented runtime scope.

** Documentation and verification

Use Org files, =#+begin_src= / =#+end_src= blocks, inline =code=, and relative
=file:= links. English is primary; update the matching Chinese pages together.
Keep command details in the shared [[file:../../BUILD.org][BUILD.org]]. Document implemented behavior
separately from proposals and distinguish source inspection from runtime evidence.

Start with checks appropriate to the change. For documentation, inspect all
changed and newly untracked pages for links, headings, paired blocks, whitespace,
and bilingual consistency. Use CLI help, =list=, =metadata=, and dry-run plans
to check command descriptions without building or launching programs.

=check= includes compilation. =test= builds the application and lifecycle
probe and runs the five registered runtime process tests. These tests do not
exercise Vault, remote APIs, or in-flight communication callbacks. Do not report
a dry-run or an empty test inventory as passing correctness tests. Do not run full builds
unless explicitly requested; do not run installation, deployment, or services
as incidental documentation checks. Report performed checks and unrun checks.
No automatic commit is part of documentation maintenance.
